# Требования к внешним интеграциям: сервисы «Умный дом» (интеллектуальный домофон и шлагбаум)

Диаграммы:
- `c4-context-smart-home.drawio` — диаграмма контекста C4 для новых бизнес-функций;
- `c4-containers-updated.drawio` — обновлённая диаграмма контейнеров PropDevelopment (новые элементы выделены зелёным пунктиром).

## 1. Изменения в ландшафте систем

| Элемент | Тип | Зачем нужен |
|---|---|---|
| **smart-home-service** + БД | Новый контейнер (домен ЖКУ) | Хранит права доступа (собственник → дом, подъезд, квартира, шлагбаум), гостевые пропуска, номера авто, отметки о согласиях. Это единственный компонент, который вызывает платформу партнёра. Биометрические шаблоны не хранит. |
| **Identity Provider** (Keycloak) | Новый контейнер | Единая аутентификация собственников, клиентов, партнёров и сотрудников (OIDC), MFA для критичных операций. Решает проблему нескольких точек регистрации и показа чужих данных в ЛК. |
| **API Gateway** | Новый контейнер | Единая точка входа: проверка JWT, scope и tenant, rate limit, журналирование, скрытие внутренней топологии. |
| **Partner Integration Gateway** | Новый контейнер | Единый шлюз для всех партнёрских интеграций (УК и «Умный дом»): mTLS, OAuth 2.0 client credentials, проверка подписи вебхуков, фильтрация полей (минимизация ПДн), журналирование. Применяется и к существующим API УК. |
| **Брокер событий** (Kafka) | Новый контейнер | Асинхронная доставка событий партнёра (звонок, проход, проезд, тревога) без потерь, буферизация при недоступности. |
| **Хранилище секретов** (Vault) | Новый контейнер | Хранение и ротация ключей, сертификатов и client secret интеграций. |
| **SIEM / централизованный аудит** | Новый контейнер | Журнал всех действий с доступом в дом и с ПДн, обнаружение аномалий. |
| Мобильное приложение собственника | Изменение | Новый раздел «Умный дом»: открытие двери и шлагбаума, видео с домофона, гостевые пропуска, управление номерами авто, согласие на биометрию. |
| DWH | Изменение | События «Умного дома» попадают в DWH только в обезличенном виде. Номера авто и биометрия в DWH не передаются. |

## 2. Требования к безопасности

### 2.1. Данные и законодательство

| № | Требование |
|---|---|
| S-1 | Биометрия (изображение лица, биометрический шаблон) относится к специальной категории (ст. 11 152-ФЗ). Её обрабатывают только при наличии **отдельного письменного согласия** (в том числе в форме ЭП в приложении), функция распознавания лица включается только по явному запросу жильца (opt-in). Без согласия доступны звонок и открытие из приложения. |
| S-2 | Биометрические шаблоны хранятся и сравниваются **только на стороне партнёра** (или в ЕБС, если юристы подтвердят, что сценарий подпадает под 572-ФЗ). PropDevelopment хранит только идентификатор субъекта у партнёра и статус согласия. Биометрия не передаётся в DWH и BI. |
| S-3 | Партнёр является лицом, обрабатывающим ПДн по поручению PropDevelopment (ст. 6 ч. 3 152-ФЗ). Договор поручения содержит перечень действий, цели, требования к защите, сроки хранения, обязанность уведомлять об инцидентах в течение 24 часов, право на аудит. |
| S-4 | Все ПДн (в том числе изображения с камер и номера авто) хранятся и обрабатываются **на территории РФ** (ст. 18 ч. 5 152-ФЗ). |
| S-5 | Минимизация: партнёру передаются только идентификатор жильца (псевдоним), объект доступа (дом, подъезд, шлагбаум), срок действия права, номер авто. ФИО, телефон, адрес и лицевой счёт не передаются. |
| S-6 | Сроки хранения: видеозаписи и снимки проходов — не более 30 дней (или по договору с УК), журнал проходов — по регламенту УК. Биометрический шаблон удаляется в течение 3 рабочих дней после отзыва согласия или прекращения права собственности. |
| S-7 | Классификация (см. Task1): права доступа, ключи и биометрия — **секретные данные**, номера авто и журнал проходов — **конфиденциальные**. Все ПДн шифруются при хранении (AES-256) и при передаче (TLS 1.2+ или ГОСТ TLS для каналов, где требуется СКЗИ). |

### 2.2. Доступ и изоляция

| № | Требование |
|---|---|
| S-8 | Мультиарендная изоляция: каждая команда и каждый запрос привязаны к `tenant_id` (УК) и `building_id`. Партнёр и операторы УК видят только свои дома. Проверка выполняется на API Gateway (claims токена) и повторно в smart-home-service. |
| S-9 | Право открыть дверь или шлагбаум проверяет smart-home-service по актуальным данным о собственности (CRM ЖКУ). При продаже квартиры права отзываются автоматически. |
| S-10 | Критичные операции (выдача постоянного доступа гостю, добавление авто, включение биометрии) требуют повторной аутентификации или MFA (step-up authentication). |
| S-11 | Гостевые пропуска одноразовые или ограничены по времени (TTL), подписаны (JWT/HMAC) и отзываются. |
| S-12 | Операторы УК входят в консоль партнёра через SSO (федерация с IdP) с MFA. Доступ ограничен ролями (RBAC). |

### 2.3. Надёжность и безопасная эксплуатация

| № | Требование |
|---|---|
| S-13 | Отказ интеграции **не должен блокировать выход** из дома (требования пожарной безопасности). Оборудование имеет автономный режим: физический ключ, локальный кэш прав доступа на контроллере со сроком действия. |
| S-14 | SLA платформы партнёра ≥ 99,9%, время открытия по команде из приложения ≤ 2 с. Мониторинг доступности на стороне PropDevelopment. |
| S-15 | Защита от перебора и злоупотреблений: rate limit на открытие (например, 10 команд в минуту на пользователя), обнаружение аномалий (массовые открытия, открытия из нехарактерных геолокаций). |
| S-16 | Защита от подмены биометрии: партнёр подтверждает наличие liveness detection (защита от фото и видео) и показатели FAR/FRR по результатам испытаний. |
| S-17 | Оборудование на объектах: отдельный сегмент сети (VLAN), исходящее соединение только к платформе партнёра, управление прошивками и обновлениями, отключённые сервисные учётки по умолчанию. |
| S-18 | Журналирование: каждая команда открытия, изменение прав и событие прохода записывается с `user_id`, `device_id`, `timestamp`, `correlation_id`, результатом. Журналы отправляются в SIEM, ПДн в журналах маскируются. |
| S-19 | Партнёр подтверждает соответствие требованиям ИБ: пентест не реже раза в год, отчёт SOC 2 / ISO 27001 или аттестат по требованиям ФСТЭК, процесс управления уязвимостями. |
| S-20 | Контракт API проходит согласование со специалистом по ИБ до начала разработки (security review). Изменения контракта согласуются повторно. |

## 3. Протоколы аутентификации и авторизации

| Взаимодействие | Протокол | Детали |
|---|---|---|
| Собственник → мобильное приложение → PropDevelopment | **OpenID Connect + OAuth 2.0 Authorization Code Flow + PKCE** | IdP PropDevelopment (Keycloak). Access token JWT (RS256 / ГОСТ), срок жизни 5–15 минут, refresh token с ротацией и привязкой к устройству. Scopes: `smarthome:read`, `smarthome:open`, `smarthome:manage`. MFA (OTP / биометрия устройства) для операций S-10. |
| PropDevelopment (smart-home-service через Partner Integration Gateway) → платформа партнёра | **mTLS + OAuth 2.0 Client Credentials** | Взаимная аутентификация по сертификатам (выпускает УЦ PropDevelopment, ротация сертификатов каждые 90 дней). Access token со scope на конкретные операции и `tenant_id`. Секреты хранятся в Vault. |
| Платформа партнёра → PropDevelopment (вебхуки событий) | **HTTPS + mTLS + HMAC-SHA256** подписи тела | Заголовки `X-Signature` и `X-Timestamp`, окно ±5 минут (защита от повторов), идемпотентность по `event_id`. Allowlist IP-адресов партнёра. |
| Операторы УК → консоль партнёра | **SAML 2.0 / OIDC SSO** | Федерация с IdP, MFA, RBAC по ролям УК. |
| Сотрудники PropDevelopment → админка smart-home-service | **OIDC** (федерация со службой каталогов), MFA | RBAC: `smarthome-viewer`, `smarthome-operator`, `smarthome-admin`. |
| Внутренние сервисы PropDevelopment | **mTLS** (service mesh) + JWT с передачей контекста пользователя | В Kubernetes трафик ограничен NetworkPolicy (Task5). |
| Видеопоток домофона в приложение | **WebRTC (DTLS-SRTP) или HLS по HTTPS** с одноразовым подписанным URL | URL выдаёт smart-home-service после проверки прав, TTL ≤ 60 с. |

Авторизационная модель — **ABAC поверх RBAC**. Решение об открытии принимается по атрибутам: роль (собственник, член семьи, гость), объект (`building_id`, `entrance_id`, `barrier_id`), время, статус собственности, `tenant_id` УК.

## 4. Организация взаимодействия систем

### 4.1. Общие принципы

1. **Единая точка взаимодействия.** Все вызовы к партнёру и от партнёра идут через Partner Integration Gateway. Прямые вызовы из других сервисов запрещены сетевыми политиками.
2. **Contract-first.** Контракты описываются в OpenAPI 3 (синхронные вызовы) и AsyncAPI (события), версионируются (`/v1/...`) и проходят ревью ИБ. Обратная совместимость сохраняется не менее 6 месяцев.
3. **Источник истины о правах доступа — PropDevelopment** (smart-home-service). Партнёр получает права через синхронизацию и не может создавать их сам.
4. **Источник истины об оборудовании и биометрии — партнёр.**

### 4.2. Основные потоки

| Поток | Тип | Описание |
|---|---|---|
| Регистрация жильца в «Умном доме» | Синхронный REST | Приложение → API Gateway → smart-home-service: проверка собственности в CRM ЖКУ → `POST /v1/residents` к партнёру (псевдоним, объекты, срок). |
| Включение распознавания лица | Синхронный, с редиректом | Жилец подписывает согласие в приложении → smart-home-service фиксирует согласие → партнёр получает одноразовую ссылку на захват лица в его SDK. **Фото лица не проходит через серверы PropDevelopment.** |
| Добавление номера авто | Синхронный REST | Приложение → smart-home-service (валидация формата, лимит авто на квартиру) → `PUT /v1/vehicles` к партнёру. |
| Открытие двери или шлагбаума из приложения | Синхронный REST | Приложение → smart-home-service (проверка ABAC) → `POST /v1/devices/{id}/open` с идемпотентным ключом → ответ ≤ 2 с. |
| Вызов в домофон | Асинхронный | Партнёр → вебхук `call.incoming` → брокер → smart-home-service → push в приложение → жилец принимает видеозвонок (WebRTC) и открывает дверь. |
| События проходов и проездов | Асинхронный | Партнёр → вебхук `access.granted` / `access.denied` → брокер → smart-home-service (журнал) → SIEM. |
| Синхронизация прав | Пакетный и событийный | При изменении собственности (событие CRM ЖКУ) права отзываются или выдаются. Ежедневная сверка (reconciliation) прав между PropDevelopment и партнёром с отчётом о расхождениях. |
| Отзыв согласия на биометрию | Синхронный + подтверждение | smart-home-service → `DELETE /v1/residents/{id}/biometrics` → партнёр присылает событие `biometrics.deleted`, оно сохраняется как подтверждение для аудита. |

### 4.3. Надёжность интеграции

- Таймауты (2–5 с), повторы с экспоненциальной задержкой только для идемпотентных операций, circuit breaker на шлюзе.
- Гарантированная доставка событий через брокер (at-least-once + дедупликация по `event_id`), DLQ для необработанных событий.
- При недоступности партнёра приложение показывает статус, оборудование работает в автономном режиме (S-13).
- Мониторинг: метрики задержек и ошибок по каждому методу, алерты дежурной команде, отчёт об SLA партнёра раз в месяц.

### 4.4. Пример контракта события

```json
{
  "event_id": "8b1c9e1e-...",
  "type": "access.granted",
  "occurred_at": "2026-11-23T10:15:30Z",
  "tenant_id": "uk-042",
  "building_id": "bld-17",
  "device_id": "intercom-17-2",
  "subject": { "resident_ref": "r_5f2a...", "method": "face" },
  "correlation_id": "c-7781..."
}
```

В событии нет ФИО, телефона и изображений. Ссылка на снимок, если нужна, выдаётся по отдельному авторизованному запросу с коротким сроком действия.
